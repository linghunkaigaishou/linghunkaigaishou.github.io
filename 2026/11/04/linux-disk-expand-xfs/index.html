Linux 裸盘 XFS 在线扩容：不卸载、不重启，把 2T 扩到 3T

发表于 2026-11-04
运维-LinuxXFS磁盘扩容运维

存储侧刚把卷从 2T 扩到 3T，df -hT 一看还是 2T——这大概是运维里最常遇到的一种”看起来没生效”。

其实整件事只有三步：存储侧扩容 → 内核重新识别容量 → 文件系统扩容。XFS 和 ext4 都支持在线扩容，全程不用卸载、不用重启，业务无感知。这篇按场景整理成操作手册，下次照着走即可。

先判断该走哪条路

不同磁盘形态的命令完全不同，走错分支会白折腾半天：

现状 需要做的操作
裸盘 /dev/sdb 直接挂载（无分区表） rescan → xfs_growfs /data
有分区 /dev/sdb1 rescan → growpart → xfs_growfs /data
LVM（/dev/mapper/vg-lv） rescan → pvresize → lvextend → xfs_growfs /data
文件系统是 ext4 rescan → resize2fs /dev/sdb（替换掉 xfs_growfs）

先花 10 秒确认三件事：

本案例：/dev/sdb 裸盘、无分区、XFS、挂载在 /data，2T → 3T。

操作前检查清单

  • 确认存储侧扩容已生效：云平台/虚拟化平台上 /dev/sdb 的目标容量确实已变 3T，且状态正常（有的平台需要重启实例或重新挂载才生效，务必先看清楚）。
  • 确认能回退：有条件就先打快照。XFS 只能扩、不能缩，一旦扩错只能重建文件系统。
  • 避开高峰：在线扩容通常无感知，但大容量 XFS 的 xfs_growfs 会有短暂 IO 抖动。
  • 留一份扩容前状态：方便事后对比，也方便写操作记录。

关键记忆点：**xfs_growfs 的参数是挂载点，不是设备名。**
正确 xfs_growfs /data；错误 xfs_growfs /dev/sdb。

预期：

再对一下 xfs_info 里的 data blocks：块数 × 4096 ÷ 1024³ 应当接近新容量，这个数字变化才说明文件系统真的扩了（df 有时受 inode/预留块影响，不如它直观）。

变体一：磁盘上有分区

如果 lsblk 显示 /dev/sdb1，直接 xfs_growfs 是没用的——空间在磁盘尾部，分区还没覆盖到。

注意：MBR 分区表单分区上限 2T。超过 2T 必须用 GPT，这种情况没法原地把 MBR 改成 GPT，需要新建磁盘迁移数据。

变体三：文件系统是 ext4

只是扩容命令不同，其余步骤一致：

ext4 同样支持在线扩容（在线缩容不行）。

不要顺手加 e2fsck -f：resize2fs 只是提示”建议先检查”时再考虑，而且**不要在已挂载可写的 ext4 上跑 e2fsck -f**；真要检查就卸载，或安排停机窗口。

常见坑

坑 1：fdisk -l 已经是 3T，df -h 还是 2T
磁盘容量被内核认到了，但文件系统还没扩。执行 xfs_growfs /data 就好了。

坑 2：xfs_growfs /dev/sdb 报 not a mounted XFS filesystem
参数写成了设备名。XFS 要用挂载点：xfs_growfs /data。

坑 3：rescan 之后容量纹丝不动
顺序永远是”先存储侧、再内核”。多路径、虚拟化平台、老内核 virtio 盘是三个高频原因，见上文“确认内核已识别新容量”里的排查顺序。

坑 4：想缩回去
XFS 不支持缩容，ext4 也不支持在线缩容。扩容前务必确认目标容量，重要数据先快照/备份。

坑 5：扩容完忘了改监控阈值
磁盘使用率 80% 告警是按旧容量配的，扩容后阈值和容量报表一起更新，否则下次告警还是会误报（或者该报的不报）。

坑 6：/etc/fstab 需要改吗？
不需要。挂载点、设备名都没变，只改了容量。

小结

  1. 裸盘无分区，不需要动分区表；有分区才需要 growpart；
  2. 存储侧扩完之后，必须 echo 1 > /sys/block/sdb/device/rescan 让内核重新识别；
  3. fdisk -l 确认磁盘变成新容量，再做文件系统扩容；
  4. XFS 用 xfs_growfs /data（挂载点），ext4 用 resize2fs；
  5. 最后 df -hT /data + xfs_info 双重验证，别忘了同步监控阈值。

整个过程业务无感知，但每一步都要”先确认、再执行”——尤其是“确认内核已识别新容量”这一步，没确认就扩文件系统，只会得到一个”没有任何变化”的 xfs_growfs。
